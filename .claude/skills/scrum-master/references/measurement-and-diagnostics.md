# 測定と診断

Definition of Doneや品質の低下禁止は[SG20]の規範に基づく。フロー指標（Cycle Time、WIP、Work Item Age、Throughput、SLE）は[KGS21]、EBMの重要価値領域は[EBM24]、DORA指標はソフトウェア提供限定で[DORA26]——いずれもScrum Guideを補完する公式・研究知見層であり、Scrum自体の必須要素ではない。

## 測定原則

- 指標は評価や統制ではなく、透明性、検査、適応のために使う。
- 活動量より成果、局所効率よりエンドツーエンドの価値、単一値よりバランスを見る。
- チームやサービスの文脈内で経時変化を追う。異なるチームを順位付けしない。[DORA26]
- 定量データだけで原因を断定せず、定性データと実際の仕事を併せて検査する。
- 測定コストを管理し、意思決定を変えないデータは集めない。
- 指標を目標にした瞬間にゲーム化のリスクが高まるため、望む成果とガードレールを対にする。[DORA26]

## 診断の順序

### 1. 成果

- 利用者・顧客の行動や満足
- 解決した問題、実現した価値
- Product Goalへの進捗
- 事業・ミッション上の成果

EBMを使う場合は、「組織のゴール（未実現の価値）、ゴールに対する組織の現在の状態（現在の価値）、価値の提供における組織の反応性（市場に出すまでの時間）、価値の提供における組織の効果性（イノベーションの能力）」という4つの重要価値領域（KVA）のどのギャップを改善するか決める。[EBM24, p.8]

### 2. 品質と安定性

- Definition of Doneを満たす割合
- 本番不具合、再作業、インシデント
- 技術的負債または未計画作業の傾向
- 変更失敗と復旧

「品質を低下させない。」[SG20, p.7]「完成の定義を満たさない限り、作業をインクリメントの一部と見なすことはできない。」[SG20, p.12]

### 3. フロー

- WIP：開始したが未完了の項目数
- Cycle Time：開始から完了までの経過時間
- Work Item Age：未完了項目の開始から現在までの時間
- 「スループット（Throughput）：単位時間あたりの終了した作業項目の数。」[KGS21, p.4]

分布を優先し、平均だけで外れ値を隠さない。履歴が十分なら、「サービスレベル期待値（SLE）」——「任意の項目がスクラムチームのワークフローを『開始』から『終了』へと流れるまでの時間を予測するもの」で、「経過日数とその確率」の2部から成る（例：「作業項目の85%が8日以内に終了する」）——を作り、予測と異常検知に使う。[KGS21, p.6]

### 4. 学習とチーム環境

- 改善実験の完了と検証
- 顧客・ステークホルダーフィードバックまでの時間
- 障害の滞留時間
- 異論、質問、失敗共有が可能かという定性的な観測

心理的安全性は学習の条件であり、成果指標の代替ではない。厳しい基準、率直な対話、アカウンタビリティと両立させる。[EDM99]

## 推奨指標

目的に応じ、少数を選ぶ。汎用のフロー指標（研究・実務知見層、[KGS21]）と、ソフトウェア提供限定のDORA指標（同じく研究・実務知見層だが適用範囲がより狭い、[DORA26]）を区別する——後者はソフトウェア以外の複雑な作業には適用しない。

| 改善したいこと | 結果指標 | 先行・診断指標 | ガードレール | 出典・適用範囲 |
|---|---|---|---|---|
| 顧客価値 | 利用、継続、成果達成 | フィードバックまでの時間 | 苦情、解約、品質 | 汎用（特定の単一出典なし） |
| 予測可能性 | Sprint Goal達成傾向 | Cycle Time分布、Work Item Age、WIP | 品質低下、残業 | 汎用フロー指標 [KGS21] |
| 品質 | 本番不具合、変更失敗 | 自動化、再作業、未計画作業 | リードタイム | 汎用（特定の単一出典なし） |
| 学習速度 | 検証済み仮説数 | 実験Cycle Time | 顧客影響、運用負荷 | 汎用フロー指標 [KGS21] |
| 障害除去 | 再発率、影響時間 | 障害滞留時間、所有者未設定数 | チームの自己管理 | 汎用（特定の単一出典なし） |

ソフトウェア提供を対象にDORAを使う場合は、現行の5指標を同一アプリケーションまたはサービスの経時改善に限って使う（他チームとの比較や、ソフトウェア以外の作業への適用は範囲外）。[DORA26]

- Change Lead Time
- Deployment Frequency
- Failed Deployment Recovery Time
- Change Fail Rate
- Deployment Rework Rate

## 避ける使い方

- VelocityやStory Pointsを成果、価値、生産性と同一視する。
- Velocityをチーム間比較、人事評価、コミットメントに使う。
- 個人の完了チケット数、コード行数、発言回数を評価する。
- 稼働率100%を目指し、WIP、待ち時間、協働、学習を悪化させる。
- Sprint Goalを無視し、完了した項目数だけでSprintを成功・失敗と判定する。
- 一つの指標を目標にし、副作用を監視しない。
- ベースライン、期間、定義、分母が異なる数字を比較する。

Story PointsやVelocityはチーム内部の予測補助として使えるが、Scrum Guideの必須要素ではない。「開発者が過去の自分たちのパフォーマンス、今回のキャパシティ、および完成の定義の理解を深めていけば、スプリントの予測に自信が持てるようになる。」[SG20, p.8]

## 改善実験

一度に主な変更を一つに絞る。

```text
観測：
仮説：
変更：
対象範囲：
開始時点の値：
期待する変化：
ガードレール：
観測期間：
検査日：
判断基準：
```

因果を検討するときは、同時期のリリース、要員変化、季節性、障害、計測定義変更などの代替説明を確認する。データが少ない場合は「改善した」と断定せず、「改善と整合する兆候」と表現する。

## フロー指標を計算する

Cycle Time分布・Work Item Age・週次Throughput・WIPの推移を手元のチケットデータから計算する場合は、数値を創作せず`scripts/flow_metrics.py`を使う。

```bash
python3 .claude/skills/scrum-master/scripts/flow_metrics.py tickets.csv --as-of 2026-07-31
```

入力CSVの列：`item_id,started_at,completed_at`。`--as-of`は報告基準日（既定は本日）で、Work Item Ageの基準と週範囲を決める。Cycle TimeとWork Item Ageは両端を含めて数える（同日完了は1日）——これはGuideの規定ではなく実務上の慣行である。

パス・オプション・慣行の詳細は[SKILL.md](../SKILL.md)の「スクリプト：フロー指標の計算」を参照（ユーザースコープにインストール済みの場合は`~/.claude/skills/...`形式を使う。この2形式が`.claude/settings.json`の`permissions.allow`に登録されている）。
