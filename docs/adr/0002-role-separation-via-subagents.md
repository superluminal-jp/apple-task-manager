# 0002. アカウンタビリティの視点分離はサブエージェントで行い、役割別スキルを追加しない

## Context and problem statement

Scrum Guide は1つの Scrum Team に Product Owner / Scrum Master / Developers の
3つのアカウンタビリティを定義する[SG20, p.5]。個人用スクラムでは1人がこれを
すべて兼ねるため、役割分離が生む検査機会が構造的に失われる。

当初「Scrum であると言えるように、それぞれの立場のスキルを作る」案が出た。
これに対して2つの点を切り分ける必要があった。

**第一に、役割別のスキルやエージェントを作っても Scrum にはならない。**
Guide はアカウンタビリティを人に割り当てる（「プロダクトオーナーは1人であり、
委員会ではない」[SG20, p.5]、「プロダクトオーナーだけがスプリントを中止する
権限を持つ」[SG20, p.8]）。アカウンタビリティとは結果を引き受けることであり、
プロンプトは何も引き受けない（これは Guide の逐語ではなく、上記からの推論）。
生まれるのは視点であって、アカウンタビリティではない。

**第二に、それでも視点の分離自体には価値がある。** 単独運用で失われるものの
うち「利害が実際に異なる独立した視点」は、視点分離で部分的に回復できる。
（回復できないのは外部の実利用者からのフィードバックであり、これは
仕組みでは埋まらない。）

したがって論点は「Scrum の成立要件か」ではなく「視点分離をどの機構で
実装するか」に絞られた。ここで決定的な観察がある。**PO 役と Developers 役を
同一の会話で演じさせると、独立した利害を持たないため対話が即座に収束する
（偽の合意）。** 分離の価値は別の指示書を持つことではなく、
**同じコンテキストを共有しないこと**にある。

## Decision

**視点分離は、非対称なブリーフを与えた別コンテキストのサブエージェントとして
実装する。`my-claude-code` に `product-owner` / `developers` スキルは
追加しない。**

したがって：

- PO 役と Developers 役は独立したコンテキストで動き、異なる目的と
  異なる情報を与えられる。
- `scrum-master` スキルは現状のまま、ファシリテーター／検査役として残る。
  既存の狭いルーティング定義を変更しない。
- 本システムは「個人用 Scrum」ではなく「経験主義を単独作業に適用する仕組み」
  として文書化する（README §0）。

### Alternatives considered

**`my-claude-code` に `product-owner` と `developers` スキルを追加する。**
却下。スキルには既に配布経路（`install.sh` の `CUSTOM_SKILLS`）と
ルーティング機構があり、インフラ費用はゼロという実利があった。却下理由は2つ。
(1) スキルは `.claude/CLAUDE.md` の**常時読み込まれるルーティング一覧**に載る。
`.claude/rules/skill-routing.md` は `scrum-master` について
「常時読み込まれるルーティング一覧に載るため、意図的に狭くしている」と
明記しており、Scrum 系スキルを3つに増やすと毎ターンの分岐が増え、
かつ3者間のルーティングが曖昧になる。
(2) より重要なのは、スキルは同一会話にロードされるため**コンテキストを共有し、
偽の合意という核心的な失敗モードを解決しない**こと。

**既存 `scrum-master` スキル内の3スタンスとして表現する。** 却下。
同スキルには既に「支援モード」（ティーチャー／メンター／ファシリテーター／
コーチ等）という同型の機構があり、一貫性という利点があった。しかし帽子の
切り替えを同一コンテキストで宣言するだけでは分離が最も弱く、上記の
偽の合意問題をそのまま残す。

**視点分離を実装せず、決定権の明文化（運用規約）のみとする。** 部分的に採用。
「どの判断を PO の帽子で下すか」を Notes に明文化することは Sprint 1 に含める。
これ単独では不十分だが、**役割分離の効果の大半はここで出る**と判断しており、
サブエージェントはその上に載る補強である。規約なしでエージェントだけ作ると、
人間側の判断基準が空のまま対話だけが増える。

## Consequences

- 肯定：非対称なコンテキストにより、対話が即座に収束する偽の合意を避けられる。
- 肯定：`my-claude-code` の常時ロードされるルーティング表を汚さない。
  サブエージェントはルーティング一覧に載らない。
- 肯定：`scrum-master` スキルの既存の狭い定義とテスト（routing 回帰）に
  手を入れずに済む。
- 否定：**`my-claude-code` には現時点で `.claude/agents/` が存在せず、
  `install.sh` の配布対象は `CUSTOM_SKILLS` の8スキルのみでエージェントの
  配布経路がない。** サブエージェントを選ぶと同リポジトリに新しい成果物
  カテゴリと配布経路を作る作業が発生する。スキル追加ならこの費用はゼロだった。
- 否定：サブエージェントは毎回コールドスタートで、文脈を再導出する。
  同一会話でスタンスを切り替えるより実行コストが高い。
- 否定：この仕組みは Scrum のアカウンタビリティを回復しない。README §0 の
  但し書きを維持し続ける責任が残る。放置すると「Scrum をやっているつもり」に
  退行する。
- 中立：`.claude/agents/` を `my-claude-code` に新設する場合、その配布機構は
  同リポジトリ側の決定であり、そこで別途 ADR が必要になる。本 ADR は
  他リポジトリの構造を先に決めない。
- **後から判明した制約**：`my-claude-code` は本設計の直前のコミットで
  `scrum-master` から solo/個人利用の記述を削除しており（BREAKING CHANGE：
  personal/solo Scrum Master requests を自動ルーティングしない）、
  `skill-routing.md` に solo/personal/個人 の記述は1件も無い。
  本決定の方向——個人運用の作法を共有スキルに持たせない——を独立に裏付ける
  一方で、**個人スクラムの相談が `scrum-master` に自動ルーティングされない**
  ことを意味する。検査役が自動で立ち上がる前提は成り立たないため、
  本システム側が入口を用意する必要がある。入口の形は Sprint 1 で決める。

## Confirmation

- Sprint 1 に「PO 役・Developers 役サブエージェントの初版（非対称なブリーフ）」と
  「決定権の明文化」の両方が含まれる（README §5）。
- Sprint 2 の判断ポイントで、視点分離が実際に有効だったか——具体的には
  PO 役と Developers 役の対話が偽の合意に終わらず、backlog の順序や
  容量見積りに実際の変更をもたらしたか——を検査する。
- `my-claude-code` の `.claude/CLAUDE.md` のスキル一覧と
  `.claude/rules/skill-routing.md` に Scrum 系スキルが追加されていないことで、
  本決定の遵守が確認できる。
